A practical command-line field guide

Hermes, Kanban
& profiles.

Use Hermes Agent from a terminal, keep different assistants in separate profiles, and move work through Hermes’ built-in task board. Start with commands you can type today, then see how all three pieces fit together.

CLI examples checked against Hermes Agent v0.19.0 on October 23, 2026. Hermes changes over time; your installed hermes --help is the final reference.

Start here

Run these read-only commands first to see your Hermes install, profiles, and boards:

hermes --version
hermes --help
hermes profile list
hermes kanban boards list
hermes kanban list

Hermes is the assistant runtime and command-line interface. A profile selects an agent identity and its configuration. A Kanban board stores tasks; a task can be assigned to a profile and claimed by a worker. A board is a local task queue, not a GitHub Issues board.

Safe first move: inspect with list, show, boards list, profile list, and --dry-run. Creating or dispatching work can change task state or start model calls.

Using Hermes from the terminal

Hermes supports interactive chat plus subcommands for setup, profiles, Kanban, gateway services, and configuration. Learn the command tree on your installed version:

hermes --help
hermes kanban --help
hermes profile --help
hermes kanban create --help

Start an assistant session

# Start an interactive chat in the current terminal
hermes

# Start a named profile directly
hermes -p researcher chat

# Send a single prompt and exit
hermes -p researcher -z "Summarize the open TODOs in this repository."

Hermes starts in your current working directory. Change to the project first so repository instructions and tools apply to the intended code. A profile’s Hermes home is separate from the shell’s working directory; set terminal.cwd in the profile’s configuration if it should always start in a specific project.

Use local help as the source of truth

Flags and Kanban states evolve. Ask the installed CLI for a specific command before scripting it. For shell automation, use --json where available, check exit status, and avoid parsing pretty terminal tables.

Profiles: separate Hermes workspaces

A profile is a named Hermes instance with its own home directory and settings. Profiles help separate roles, model defaults, skills, memory, sessions, and tool setup—for example a researcher, a writer, and a code reviewer. This is application-level organization; profiles are not Linux user accounts or security sandboxes.

List, inspect, and choose a profile

hermes profile list
hermes profile show researcher

# Make researcher the sticky default for later commands
hermes profile use researcher
hermes profile use default

# Select a profile for only this invocation
hermes -p researcher chat

hermes profile use NAME changes the sticky default. The -p NAME option selects a profile for one command without changing that default. Profile selection is not the same as selecting a model; model configuration is managed separately.

Create profiles for clear roles

# Create a new profile with a useful routing description
hermes profile create researcher --description "Finds and summarizes source-backed answers."

# Clone setup from the active profile
hermes profile create reviewer --clone

# Describe an existing profile for Kanban routing
hermes profile describe reviewer --text "Reviews patches for correctness and regressions."

Use a short description that says what the profile does well. The Kanban decomposer can use descriptions to route work; names alone are a weak signal. After creation, inspect hermes profile show NAME, configure the model and tools it needs, and set up credentials deliberately.

Cloning may copy secrets. In the referenced CLI, --clone copies config, .env, SOUL.md, and skills, but not sessions or the state database. Review the destination profile before use. --clone-all copies substantially more state; choose it only when intended.

Aliases and lifecycle

# Create or refresh a shell wrapper for a profile
hermes profile alias researcher

# Rename a profile
hermes profile rename researcher research

# Export and restore as a different profile
hermes profile export research -o ./research-backup.tar.gz
hermes profile import ./research-backup.tar.gz --name research-restored

Aliases are convenience wrappers, not separate agents. Exports omit credential stores, but still treat profile archives as private because they can include configuration, memory, skills, and prompts. Deleting a profile removes its files and data; inspect hermes profile --help before destructive lifecycle operations.

Kanban: durable tasks for profiles

Hermes Kanban stores tasks in a local SQLite-backed board and coordinates work across profiles. Tasks can be assigned, linked by dependencies, claimed, commented on, blocked, scheduled, reviewed, and completed. They can use scratch or Git worktree workspaces.

Boards separate workstreams

# List boards and inspect the active board
hermes kanban boards list
hermes kanban boards show

# Create a board and switch to it
hermes kanban boards create tessarchy --name "Tessarchy" --switch

# Switch boards, or specify one for a single command
hermes kanban boards switch default
hermes kanban --board tessarchy list

Use a different board for another project or queue. Tasks and dependencies stay within their board. Check the active board before creating or dispatching work so a task does not land in the wrong queue.

Task statuses at a glance

triage→todo→ready→running→review→done
StatusMeaning in use
triageNeeds a clearer brief or decomposition before execution.
todoAccepted work waiting for prerequisites or promotion.
readyEligible for an assigned worker or dispatcher to claim.
runningA profile has claimed and is executing the work.
reviewImplementation is handed off for review or approval.
blockedWaiting for a person, capability, or external condition.
scheduledParked until a later time or follow-up.
doneCompleted; record the outcome.

Dependencies express ordering: a child stays unavailable until parent work completes. Use block when a person or missing capability must intervene; use schedule for a time-delayed follow-up. A dependency is not a human blocker.

A practical terminal workflow

1. Write a task another profile can finish

Make the title an outcome. Put context, constraints, scope, acceptance criteria, and expected evidence in the body. Avoid vague titles like “fix things.”

hermes kanban create "Document the install flow" \
  --body "Read the current install docs. Add prerequisites, exact commands, recovery steps, and links. Do not change installer code. Report changed files and checks performed." \
  --assignee writer \
  --workspace scratch

Assignment routes work to a profile; it does not mean the task is automatically safe, correct, or reviewed. Keep acceptance checks verifiable.

2. Use worktrees for code changes

hermes kanban create "Add phone launcher keyboard navigation" \
  --body "Implement the change in the project and report the affected files and validation evidence." \
  --assignee the-coder \
  --workspace worktree \
  --branch wt/phone-launcher-keyboard

scratch is for isolated temporary work; worktree creates an isolated Git worktree; dir:/path uses a directory you choose. Worktrees reduce collisions, but inspect the diff and branch before integrating changes.

3. Inspect before dispatch

hermes kanban list --status ready
hermes kanban show TASK_ID
hermes kanban context TASK_ID
hermes kanban dispatch --dry-run

The context command shows task details, parent results, and comments available to a worker. Dry-run previews dispatcher decisions without spawning workers. A real dispatch can start model calls and code changes.

4. Run or monitor the work

# Manually launch one dispatcher pass after reviewing the dry run
hermes kanban dispatch --max 1

# Inspect the task and follow its event stream
hermes kanban show TASK_ID
hermes kanban tail TASK_ID
hermes kanban runs TASK_ID

The gateway can run the embedded dispatcher when enabled; hermes kanban dispatch is a manual one-pass operation. In current builds, hermes kanban daemon is deprecated; use hermes gateway start to start the gateway service. Do not run a persistent dispatcher unless you intend ready tasks to launch automatically.

5. Review and close the loop

# Add a clarification or request for the handoff
hermes kanban comment TASK_ID "Please include the command output in the handoff."

# Record a completed task's result
hermes kanban complete TASK_ID --result "Added the guide and verified the rendered page."

Review resulting files, commits, and validation evidence yourself. If another pass is needed, use the review/change actions shown by your installed CLI. Record concrete outcomes, not a generic “done.”

Use hermes kanban --board NAME ... for one-off commands on a non-active board. To pin a board for the current shell, set HERMES_KANBAN_BOARD; switching a board stores the default for later invocations.

Troubleshooting and good habits

  • Command not found: check the install and shell path with command -v hermes and hermes --version; restart the shell after changing PATH.
  • Wrong board: run hermes kanban boards show, then use --board SLUG for a one-off.
  • No work starts: inspect ready tasks, assignments, dependencies, gateway status, and hermes kanban dispatch --dry-run. Tasks in todo or blocked are not ready to claim.
  • Unknown assignee: check hermes profile list and use the exact profile name. Profile descriptions improve task routing.
  • Task stuck running: inspect events and run history first. Reclaiming affects shared state, so use recovery commands only after confirming that its worker is gone.
  • Different behavior: inspect that subcommand’s local --help. Upstream docs may describe a newer release.
Keep tasks reviewable. Split independent outcomes, link true prerequisites, assign profiles with matching skills, and verify the result before closing or integrating it.

Hermes Kanban vs. the Tessarchy queue

This guide describes hermes kanban, Hermes Agent’s multi-profile board. Tessarchy also contains scripts/agent-kanban.py, a separate read-only prototype for suggesting stages for GitHub issues. That script does not use Hermes’ SQLite board, assign Hermes profiles, dispatch agents, edit issues, or create a GitHub Projects board.

Read the Tessarchy Agent Kanban notes for its setup and limits. Do not use the Python prototype’s commands as if they control Hermes profiles.
